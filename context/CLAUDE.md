# CLAUDE.md

Guidance for Claude Code when working in this repository. Part A describes the
project; Part B contains the operating directives, adapted from the Note (Flutter)
directives to Spotfile's stack.

# Part A — Project

## What This Is

Spotfile is a local, privacy-first semantic file search app: a native desktop
application built with [Wails](https://wails.io/) v2 — Go on the backend,
Svelte + TypeScript on the frontend, compiled into one binary with an embedded
webview (WKWebView on macOS, WebView2 on Windows). Embeddings are computed by
llama.cpp's `llama-server`, run as a child process on `127.0.0.1`.

## Commands

```bash
wails dev                       # Full dev mode with hot reload
wails build                     # Production binary → build/bin/

cd frontend && npm install      # Frontend dependencies
npm run check                   # svelte-check (types)
npm test                        # Vitest: stores, lib, token contrast floor
npm run build                   # Frontend assets → frontend/dist/

go vet ./...                    # Also: GOOS=windows go vet ./...
go test -race ./...             # Real-model tests skip without llama.cpp + model
SPOTFILE_REQUIRE_LLAMA=1 go test -race ./engine/...   # Fail instead of skip (CI)
```

Runtime requirements: `llama-server` (`brew install llama.cpp`) and
`~/.spotfile/models/bge-small-en-v1.5-f16.gguf` (see README).

## Architecture

- **`main.go`** — Wails entry point: embeds `frontend/dist`, window and macOS menu options, binds `App`.
- **`app.go`, `indexing.go`, `search.go`, `files.go`** — the `App` struct, split by concern. Exported methods become frontend bindings. Keep this layer thin: validate, log, emit events, delegate to `engine/`.
- **`engine/`**
  - `llamaserver/` — lifecycle of `llama-server` child processes (start on demand, health, idle stop, crash restart, never outlives the app).
  - `embedder/` — bge-small-en-v1.5 embeddings over llama-server (`embeddertest/` holds shared test helpers).
  - `extract/` — PDF page text and word-window chunking.
  - `indexing/` — priority queue, read → chunk → embed pipeline, file watcher.
  - `vectorstore/` — in-memory chunk store, search, versioned gob persistence (`~/.spotfile/store.gob`).
  - `llm/` — placeholder for answer generation.
- **`frontend/src/`**
  - `App.svelte` — shell: sidebar + `svelte-spa-router` (hash routes); `routes.ts` registers destinations and sidebar entries together.
  - `stores/` — `engine.ts` (all backend events, reducer), `search.ts`, `theme.ts`; `app.ts` wires them to Wails.
  - `views/search/` — search page components; `viewers/` — PDF/text previews.
  - `ui/` — design-system primitives (`PressableSurface`, `Button`, `Sidebar`, `Icon`).
  - `styles/` — `tokens.css` (all design tokens), `fonts.css`, `global.css`; `lib/` — pure helpers.
- **`frontend/wailsjs/`** — generated by Wails. Never edit by hand.
- **`.github/workflows/ci.yml`** — lint, tests on macOS/Linux/Windows with real llama.cpp and a memory budget, benchmarks, builds, tag releases.

### Frontend ↔ backend

1. Add an exported method to `App`.
2. `wails dev` / `wails build` (or `wails generate module`) regenerates `frontend/wailsjs/`.
3. Import it in Svelte from `../wailsjs/go/main/App.js`.
4. Long-running work returns immediately and reports progress through `EventsEmit`; every emitted event (including `*:error`) must have a frontend listener.

# Part B — Operating Directives

Primary goal: rigorous, test-driven logic and exceptional, anti-slop desktop UI.
Do not rush to execution.

## 1. Project Context & State Sources

Before proposing solutions or generating code, inspect and internalize these if they exist:
- **`PRODUCT.md`** — target audience, product voice, domain constraints (maintained by `impeccable`).
- **`context/DESIGN.md`** — the source of truth for design tokens: colour ramps, typography scale, spacing, radii, motion, elevation.
- **`context/ROADMAP.md`** — what is built, in progress and planned, plus tracked gaps. Check it before planning.
- **`context/PERFORMANCE.md`** — how indexing, search and inference are made fast and memory-bounded, with measured numbers. Check it before touching the engine.
- **`.claude-mem/`** — persistent memory; check historical context and prior architectural decisions before asking redundant questions.

## 2. Core Workflow (Plan → Test → Execute)

Follow the `superpowers` and `get-shit-done` methodology:
1. **Plan:** never write production code for a new feature without an implementation roadmap (`/writing-plans`).
2. **TDD:** write failing tests first.
   - **Go:** table-driven tests; `go test -race`. Anything touching models runs against the real `llama-server` via `embeddertest`, and must pass with `SPOTFILE_REQUIRE_LLAMA=1`.
   - **Memory/performance:** changes to indexing or inference keep `TestIndexPeakMemory` within budget; benchmarks use realistic corpora.
   - **Frontend:** `svelte-check` and `npm test` (Vitest) must pass. Put logic in stores and `lib/` pure functions so it is unit-testable; token changes must keep `tokens.test.ts` green. Component and visual-regression tests (the counterparts of Flutter widget/golden tests) are not set up yet.
3. **Isolate:** one branch per change; if operating via `vibe-kanban`, stay within the assigned branch/worktree.
4. **Keep the living docs current, in the same branch as the change:**
   - **`ROADMAP.md`:** tick or add items when a feature, piece or gap lands, starts, or is deferred. Every implementation plan ends with a task that updates it.
   - **`PERFORMANCE.md`:** update it when a change affects indexing, search, inference, memory or startup (models, batch sizes, concurrency, buffers, process lifecycle). Record measured numbers with the machine they came from, never estimates presented as results. If a change has no performance effect, say so in the PR instead of editing the doc.

## 3. Frontend & Design Craft (Svelte Adaptation)

- **Taste & anti-slop (`taste-skill`):** avoid template looks — uniform card grids, generic shadows, grey-on-white surfaces, excessive dividers, default accent colours. Use whitespace, hairlines and deliberate hierarchy; follow the three-plane model in `context/DESIGN.md`. Keep layouts dense, legible, intentional.
- **Motion & interaction (`emil-design-eng`):**
  - Transitions feel tactile: use the easing tokens (`standard`, `enter`, `exit`, `emphasized`) and the press spring (`--ease-press` as a CSS `linear()` curve, or `svelte/motion`'s `spring`) — never linear or abrupt curves.
  - Animate only `transform` and `opacity` (compositor-friendly); use CSS transitions and Svelte `transition:` directives for state toggles.
  - Interactive elements have hover, `:focus-visible`, pressed and disabled states.
  - Animate only state changes, layout shifts, or feedback — never decoration. Durations come from motion tokens, which collapse to `0ms` under `prefers-reduced-motion: reduce`.
- **Critique & polish (`impeccable`):** run `/impeccable critique` against `context/DESIGN.md` and `PRODUCT.md`, and `/impeccable polish` before declaring a component or screen complete.

## 4. MCP Servers & External Integrations

- **`n8n-mcp`:** for backend integrations, webhooks or automation triggers, validate node schemas and draft workflows with the n8n tools instead of guessing API contracts.
- **Browser automation (`browser-use` / Claude in Chrome):** `wails dev` serves the app to a browser at `http://localhost:34115` with working Go bindings — use it to inspect the DOM and verify rendering and layout. Native-only behaviour (window, menus, file dialogs, full screen) must be checked in the built app.
- **`claude-mem`:** persist critical decisions, state patterns and architecture deviations so future sessions stay aligned.

## 5. Standard Commands & Triggers

- **"Plan this feature"** → break down into Go engine/API layer, `App` bindings + events, frontend state (stores), component hierarchy, and test checkpoints.
- **"Polish the UI"** → audit components with `taste-skill`, apply `emil-design-eng` motion, and cross-check every value against `context/DESIGN.md` tokens in `frontend/src/styles/tokens.css`.
- **"Verify build"** → `gofmt -l`, `go vet ./...` (plus `GOOS=windows`), `go test -race ./...`, `npm run check`, `wails build`; resolve all warnings.
- **"Verify in browser"** → run `wails dev` and test end-to-end at `http://localhost:34115` with browser automation.
- **"Remember this"** → save the insight, preference or rule to `claude-mem`.

## 6. Code Style & Architecture Constraints

### Go
- `gofmt`/`goimports` formatting; import groups: standard library → `spotfile/...` → third-party.
- Wrap errors with context (`fmt.Errorf("…: %w", err)`); never swallow them; typed/sentinel errors where callers branch (`llamaserver.ErrNotFound`, `*vectorstore.StaleError`).
- Accept `context.Context` for anything blocking or I/O-bound; no goroutine without a clear owner and shutdown path.
- Keep the `App` layer thin; business logic lives in `engine/` packages with small, focused files.

### Svelte & TypeScript
- Strict TypeScript; avoid `any` unless unavoidable (type event payloads).
- Components stay presentational; state transitions, side effects and binding calls live in stores or `lib/` modules with a single source of truth. Prefer derived (`$:`) state over duplicated state.
- Never call bindings or do heavy work at the top level of a component's markup; use `onMount`, and clean up listeners/subscriptions in `onDestroy` (or the returned cleanup).
- Split large components into focused child components rather than growing one file.
- Put reusable design-system primitives (e.g. `PressableSurface.svelte`) in a dedicated `frontend/src/ui/` folder.

### Design tokens (`context/DESIGN.md`)
- Never hardcode hex colours, raw `px` spacing/radii, or font declarations in component styles.
- All tokens live as CSS custom properties in `frontend/src/styles/tokens.css`; components use `var(--…)`.

### Formatting & warnings
- Relative imports within a feature folder; avoid deep `../../..` chains (add a Vite/TS path alias instead).
- Treat compiler, `go vet`, and `svelte-check` warnings as errors. Never add `//nolint`, `// @ts-ignore`, `// @ts-expect-error`, or `<!-- svelte-ignore -->` without explicit user approval.
